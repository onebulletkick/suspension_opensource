# 02 设计目标

## 这章解决什么问题

悬架设计目标不是“更快、更轻、更硬”这样的口号。它应该是一次翻译：把规则、design event 证据要求、整车概念、团队资源、跨组接口和验证能力，翻译成悬架组能执行、能复核、能更新的设计输入。

本章是学习路线层的快速章节。读完后，你应该能建立第一版目标表，知道哪些内容是规则 gate，哪些是工程目标，哪些只是偏好或待验证假设。更完整的年度目标、接口矩阵和证据成熟度见 [高级 01 设计目标](advanced/01-design-targets.md)。

## 学习目标

- 知道设计目标必须来自可追溯输入，而不是只来自旧车习惯或个人感觉。
- 能把规则、车辆概念、资源限制和验证计划写进同一张目标表。
- 能区分 `约束 constraint`、`目标 target`、`偏好 preference` 和 `假设 assumption`，并把 `待验证 pending verification` 写进可信度或假设状态。
- 能向其他组说明悬架需要什么输入、会交付什么输出，以及谁负责确认。

## 目标从哪里来

设计目标通常来自六类输入。初学者容易只看性能愿望，但 design event 和真实工程评审更关心：目标为什么合理、证据从哪里来、边界是否清楚、后续如何验证。

| 输入来源 | 要问的问题 | 悬架目标中的表达 |
| --- | --- | --- |
| 当前规则与赛事文件 | 今年适用哪个规则版本、event handbook、设计文件模板和技术检查要求？ | 规则 gate、检查日期、负责人、不能被性能目标覆盖的硬约束 |
| 整车概念 vehicle concept | 今年的车优先可靠完赛、低速灵活、稳定可预测、轻量、可维护，还是特定动态项目表现？ | 几何、轮端刚度、行程、可调范围、结构裕度和测试优先级 |
| 团队资源 | 新队员能力、预算、加工能力、采购周期、软件熟练度、测试日数量够不够？ | 目标复杂度、可制造性、可验证性和方案取舍 |
| 上一代经验 | 哪些问题是实测或多次复现，哪些只是单次反馈或推测？ | 改进问题清单，区分现象、可能原因和待验证项 |
| 跨组接口 | 车架、气动、传动、制动、人机、制造和测试会限制什么？ | 坐标系、包络、载荷路径、维护空间、交付日期和确认人 |
| 验证能力 | 目标能否通过计算、仿真、台架、实车测试或设计评审检查？ | 验证方法、最低证据、数据通道和更新触发条件 |

规则和评分资料不要被写成永久通用答案。FSAE、FSG、FS UK、FSC 等赛区的文件会随年份变化；公开评分表适合提醒“裁判会看证据链”，不适合直接合并成所有赛事都适用的分值口径。

## 分清类型和状态

| 类型 | 判断方法 | 示例写法 |
| --- | --- | --- |
| 约束 constraint | 不满足就不能参赛、不能制造、不能装配或存在安全风险 | 规则版本已核对；轮辋内包络必须避让制动和转向件；车架安装空间由底盘组确认 |
| 目标 target | 方案希望达到的工程表现，可用证据检查 | 改善低速弯响应；提高制动入弯可预测性；增加可重复的外倾/前束调校能力 |
| 偏好 preference | 多个可行方案之间的倾向，不能压过约束 | 优先使用团队熟悉的加工方式；优先减少专用件；优先沿用已验证的连接形式 |
| 假设 assumption | 设计早期用于启动计算、包络或沟通的输入，证据还不完整 | 先用估算质量启动轮端刚度计算；先按采购候选轮胎建立包络 |

如果一句话没有来源、单位、负责人和验证方法，它通常还不是成熟目标。比如“车要更稳”可以作为方向，但目标表里要继续拆成制动入弯、稳态转向、颠簸通过、车手修正量、测试数据或仿真指标。

中文写作中常见的 `待验证`，含义是证据尚未关闭。
这个标签属于 `可信度 confidence` 或 `假设状态` 字段；不要放进目标分类字段。

## 初学者练习：做一张目标表

练习时不要先追求复杂公式。先把每个目标写成能追溯、能分工、能复核的一行。

| 字段 | 写什么 | 自查问题 |
| --- | --- | --- |
| 目标或约束 | 一句话说明要解决的工程问题 | 这句话能指导下一步设计，还是只是愿望？ |
| 类型 | 约束、目标、偏好或假设 | 它失败时会导致不合规、性能退化、方案不顺手，还是只是早期输入？ |
| 输入来源 input source | 规则文件、整车目标、接口会议、公开来源、测试反馈或估算 | 来源是否可追溯到文件、会议或负责人？ |
| 可信度 confidence | 实测、估算、继承经验、公开案例启发或待验证 | 是否把低可信度输入误写成最终事实？ |
| 负责人 owner | 哪个组或哪位成员负责确认 | 目标变化时谁会通知悬架组？ |
| 验证方法 verification | 计算、CAD 包络、K&C、FEA、台架、实车测试或 design event 证据 | 现在能验证，还是需要先准备数据和工具？ |
| 更新触发 | 规则、质量、轮胎、包络、制造或测试结果变化 | 触发后要重算哪些章节？ |

示例练习：

| 目标或约束 | 类型 | 输入来源 | 可信度 | 负责人 | 验证方法 |
| --- | --- | --- | --- | --- | --- |
| 悬架安装点和轮端包络满足当年规则与技术检查可视性要求 | 约束 | 官方规则资源页、技术检查清单 | 待验证 | 悬架 + 底盘 | 规则 gate 表、CAD 包络、装车检查 |
| 低速弯响应要比上一版调校更容易被车手控制 | 目标 | 车手反馈、测试复盘、整车概念 | 继承经验 + 待验证 | 悬架 + 测试 | 方向盘角、横摆响应、车手评分、参数对比 |
| 优先减少难加工的专用件 | 偏好 | 制造资源、预算、交付周期 | 估算 | 悬架 + 制造 | 制造评审、BOM、加工风险清单 |

## 不要把口号当目标

“更快”要回答在哪个 event、哪个工况、用什么证据判断；“更轻”要说明是否牺牲可靠性、维护性或制造周期；“更硬”更危险，因为更高刚度可能改善姿态控制，也可能放大轮胎动载、降低机械抓地或让测试难以调校。

更好的写法是：

| 口号 | 改写成可检查目标 |
| --- | --- |
| 更快 | 明确目标工况，例如低速连续弯响应、制动入弯稳定、出弯牵引或 endurance 可靠完成率 |
| 更轻 | 明确质量目标来自整车概念，并列出强度、刚度、制造和验证边界 |
| 更硬 | 明确是车身姿态控制、平台高度、转向响应还是结构刚度，并说明测试或仿真如何验证 |
| 更高级 | 明确新软件、新结构或新材料解决什么工程问题，以及团队是否有能力验证 |

## 和其它组的接口

目标阶段就要把接口说清楚。晚到的接口会让硬点、弹簧阻尼、载荷工况和结构校核反复返工。

| 接口对象 | 悬架需要对方提供 | 悬架需要交付 |
| --- | --- | --- |
| 底盘 / 车架 chassis / frame | 安装空间、主结构节点、坐标系、制造边界 | 安装点需求、支座载荷方向、维护空间 |
| 气动 aero / bodywork | 目标车高、姿态敏感性、地板和车身包络 | 行程窗口、侧倾/俯仰控制目标、杆件外露边界 |
| 传动 drivetrain | 半轴、电机、链线或差速器包络 | 轮心、行程、后悬杆件空间和极限姿态检查 |
| 制动 brakes | 制动盘、卡钳、轮毂、油管和散热空间 | upright 包络、轮辋内间隙、制动入弯目标 |
| 转向 steering | 齿条位置、行程、转向角、转向柱空间和转向力矩目标 | 主销参数、upright 转向臂、拉杆点、bump steer 目标和极限转向+跳动检查 |
| 人机 ergonomics | 驾驶员姿态、踏板、转向柱、逃生和维护边界 | 前舱杆件避让、调整件可达性、规则优先边界 |
| 制造 manufacturing | 工艺能力、材料、夹具、公差和外协周期 | 零件复杂度、关键公差、可替换件策略 |
| 测试 testing | 场地、传感器、数据采集、车手和测试日程 | 调校矩阵、验证方法、复测条件和问题清单 |

## 最低输出

完成本章练习后，至少应形成这些公开安全的交付物：

- 悬架目标表：目标、类型、输入来源、可信度、负责人、验证方法和更新触发。
- 规则 gate 表：规则版本、检查日期、适用赛区、悬架相关条目和未关闭问题。
- 跨组接口表：接口对象、输入、输出、单位、坐标系、版本和确认状态。
- 风险清单：哪些输入是估算、继承经验、公开案例启发或待验证。
- 设计证据计划：哪些目标准备通过计算、仿真、制造评审、测试或 design event 说明来证明。

这些输出不要包含受限原始数据、未经授权图表、内部代号或能反推出历史车辆细节的参数组合。公开文档应教方法和判断边界，项目自己的具体数据应放在团队内部设计记录中。

## 常见错误

- 直接复制旧车目标，没有重新检查规则、整车概念、轮胎、包络、制造和测试能力。
- 把单一赛区或旧年份评分表当成通用规则。
- 只写“提升操稳”，没有拆成车手能感知、模型能预测、测试能验证的问题。
- 只和底盘确认安装空间，忽略气动、传动、制动、人机、制造和测试接口。
- 把公开车队报告里的参数选择当成自己的目标，而不是只学习报告结构和证据组织方式。
- 目标表没有待验证标签，导致估算值在后续章节里被当成已确认输入。
